  <p>Our current site workflow just wasn't keeping up with our needs. As a services company we spend all our time on our clients' projects, and our own site often becomes the cobbler's kids' shoes.</p>
  <p>I'd wanted to update the site for a while. We built the current one in collaboration with some of the biggest leaders in technology several years ago. It needed to be fast, it needed to be secure, and it needed to stay up to date. We went with a static site generator and hosted it on Netlify. It worked great.</p>
  <p>When Pantheon announced their Next.js hosting support, I was excited to migrate our site to it and use the same approach for <strong>fastforward.sh</strong>. So I sat down one weekend and tried to see if I could migrate the whole site using Claude Code to do the heavy lifting. The plan:</p>

  <ul>
    <li>Migrate from our headless setup — a WordPress CMS with a Gatsby front end.</li>
    <li>Make sure we got all the content — 100% parity.</li>
    <li>Improve our site load speeds.</li>
    <li>Move to using MDX files for our content editing.</li>
  </ul>

  <h2>Every migration follows the same plan</h2>
  <p>Migrations all follow the same arc:</p>
  <ul class="check-list">
    <li>Discovery</li>
    <li>Plan</li>
    <li>Export</li>
    <li>Content Mapping / Architecture</li>
    <li>Import</li>
    <li>Test &amp; iterate</li>
  </ul>

  <p>We've been doing migrations for over a decade now. They always involve the same process, but they are very labor- and time-intensive. There are lots of tools, plugins, and services that can help — and invariably we still involve a lot of human interaction to review and edit the work. Because it takes so long, the scope generally increases along the way. If you're going to put this much work into a replatform, you might as well review all the content, fix any issues, and add the features you were always hoping for.</p>

  <p>I wanted to see if I could keep this as tight a scope as possible. That was a little easier here because I'm the developer — and one of the founders of the company, and therefore one of the key stakeholders.</p>

  <p>I started by creating a new project on my computer in a sibling folder to where the code for my existing site lived. Then I put Claude in plan mode and gave it a set of instructions to start our plan.</p>

  <h2>Exports</h2>
  <p>Our site had content in two places. We had ACF flexible layouts for our case studies, and we had some hard-coded blocks in our Gatsby templates for a few of our pages. This is definitely not best practice, but I remember launching this site in a hurry while also trying to build it as a team. That's not uncommon with any site.</p>
  <p>There are so many ways to structure content on sites these days. I think WordPress in particular suffers from its own flexibility. Content can live in ACF shapes, in custom content types, hard-coded in template files, in Gutenberg, in reusable WP patterns, or in page builders like WPBakery, Kadence Blocks, and Elementor — to name a few.</p>
  <p>This is where Claude seems to have a ton of potential. Sniffing out all those patterns and rationalizing and normalizing them back into content, stripping out visual decoration where appropriate, is really powerful. There are a lot of tools we've worked with for this, including some pretty good scraping tools, but adding AI to the mix is a real workhorse. There are just so many opportunities for variability in a site that LLMs can address on a page-by-page basis without human intervention.</p>

  <h2>Initial impressions</h2>
  <p>For our site, this was a pretty great way to get where we wanted to go. I've wanted to consolidate our content into our site for a while now. The majority of the writing is done by a few of us, and we're all developers. When we do work with a collaborator, we draft in Google Docs or Office 365, and then it falls on me or Rob to put the final content in the page.</p>
  <p>A static site generator paired with the multidev workflow on Pantheon is perfect for this. We write drafts in Google Docs, set the draft into an MDX file, and publish to a multidev with placeholders for our images. Then our creative director sources and touches up the images for the page. We drop those in when we're done and publish.</p>

  <h2>Other considerations</h2>
  <p>This approach isn't free. There are a few things we give up by leaving WordPress behind:</p>
  <ul>
    <li><strong>Plugin functionality.</strong> We lose a lot of functionality that's already available in plugins. We don't have a form plugin like Gravity Forms, so we'll have to figure out the best way to replace that. For us, we don't spend much time building forms — a simple contact form that securely passes data to Monday.com would go a long way.</li>
    <li><strong>Scaffolding new content.</strong> We still need to address writing new content. Even WordPress's simplification tools — like a post-clone plugin — make it really easy to stub out a new page and give the editor a clear view of what to do. I'm thinking about setting up some Claude skills, such as <code>/new-page</code>, <code>/new-case-study</code>, or <code>/edit-content</code>, that would drop in some lorem ipsum and set up a new page for editing.</li>
    <li><strong>Draft versus public content.</strong> We lose that functionality from WordPress, which we used a lot. We're going to have to see if we can build it into the frontmatter of a page and hide the content by environment.</li>
  </ul>

  <h2>Conclusion</h2>
  <p>Would I recommend this for everyone? Not as a drop-in replacement for WordPress. You trade a familiar plugin ecosystem for version control, speed, and simplicity — and you rebuild the conveniences you relied on, like forms, content scaffolding, and draft-versus-public, on your own terms.</p>
  <p>But for a small, developer-led team whose writing already lives in Google Docs, that trade is exactly the one we wanted to make. The weekend proved the part I most wanted to test: the migration itself — discovery, export, scaffolding, and the grind toward visual parity — is dramatically compressed when Claude Code does the heavy lifting. What used to take weeks of crawling, scripting, and hand-checking happened in an afternoon, with the scripts and findings sitting right in front of me the whole time, reviewable and regenerable.</p>
  <p>The honest gaps are still gaps. Forms, new-content authoring, and draft state are real work we've deliberately deferred — and each one is its own next experiment. But the cobbler's kids finally have new shoes, and for the first time in years, keeping them new feels like it'll fit the way we actually work.</p>
